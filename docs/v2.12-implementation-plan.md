## Paso 1 — Modelo de datos del proyecto (núcleo, sin UI)

Nuevo módulo interno en `harness_graph.py` (no herramienta nueva — ADR-002 §3 opción 4):

```
python3 harness_graph.py --proyecto <dir>            # deriva el modelo
python3 harness_graph.py --proyecto <dir> --json     # imprime el modelo (debug)
```

Función `derive_project(spec_dir)` que consolida fuentes **ya gobernadas**:

| Dato | Fuente | Notas |
|---|---|---|
| Estado por gate (vigente / invalidado / sin recibo) | `skill_metrics.load_receipts(spec_dir)` | JSON por recibo: `gate`, `estado`, `emitido`, `rol` |
| Fase actual | presencia de artefactos en `spec/` + gates vigentes | regla: primera macro-fase con gate sin recibo vigente |
| Sprints completados | glob `spec/reports/sprint-review-*.md` | KPIs ya legibles: comentarios `<!-- ... -->` que escribe `sprint_review.py` |
| Releases | recibos con `gate == "GATE 3"` y estado vigente | |
| Lead time por gate | reutilizar `sprint_review.lead_times(recs)` | import directo, mismo patrón que `manifest_check` |
| Retrabajo | recibos `estado: invalidado` / `revocado` por periodo | |
| Arcos de feedback activos | invalidaciones del periodo (5→4 bug, 6→4 hotfix) | mapeo invalidación→arco declarado como constante |
| Aprendizajes recientes | memorias `learning` del periodo (`sdlc-memory`) | degradar a vacío si no hay memoria |

Salida: un `dict` serializable (`--json` lo imprime). Todo deriva; **cero narración, cero archivos nuevos de datos**.

## Paso 2 — Render HTML del dashboard

`render_dashboard_html(model, nodes, loops)` reutilizando la plantilla de `harness_graph.py`:

- **Sección 1 — Grafo del pipeline del proyecto**: nodos pintados por estado de su gate (verde = recibo vigente, ámbar = invalidado/revocado, gris = sin recibo), anillo en la fase actual, arcos de feedback activos resaltados (opacos los inactivos).
- **Sección 2 — Contadores**: sprints completados, releases, HU cerradas/en curso (de `traceability_matrix.py --json` si existe; si no, se omite la tarjeta — degradación, nunca error).
- **Sección 3 — Tendencias**: tabla/sparkline SVG inline de lead time por gate y retrabajo por sprint (serie de `sprint-review-NN.md`).
- **Sección 4 — Aprendizajes y acciones**: últimas memorias `learning` + acciones propuestas del último sprint review.
- Self-contained, dark theme, cero dependencias externas (mismo estándar que `docs/graph.html`).

Salida: `spec/dashboard.html` en el repo del proyecto. Se **sobrescribe** siempre (ADR-002: un archivo, "el ahora").

## Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Proyectos sin sprint reviews aún (sprint 0-1) | secciones vacías con mensaje "sin datos aún" — degradación, nunca error |
| Memorias no usadas en el proyecto | sección 4 se omite si no hay `learning` |
| HTML desactualizado percibido como verdad | `--check` en CI + sello "generado: \<timestamp\>" visible en el pie |
| Doble fuente de verdad (HTML vs MD) | el HTML es solo render; el `--check` lo garantiza estructuralmente |

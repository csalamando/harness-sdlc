Paso 1: Problem Statement

La reportería y el consumo analítico comparten la misma base que las escrituras transaccionales: una consulta pesada de reportes puede degradar o bloquear las operaciones de gobierno. Además, la ejecución serverless genera ráfagas de conexiones que una base relacional no absorbe sin un intermediario.

Paso 4: Opciones Consideradas

Opción A: Réplica de lectura + pooler integrado del servicio gestionado

  • Descripción: Primary para escritura + read replica para reportería/MCP, con pooler integrado (PgBouncer) en ambos extremos; credencial técnica read-only exclusiva por la ruta de lectura (BR-015).
  • Paved Road: Sí
  • Tecnologías: Azure Database for PostgreSQL Flexible Server + PgBouncer integrado
  • Esfuerzo estimado: 1 semana
  • Riesgos: lag de réplica < 30 s (tolerado por reportes); el tier Burstable no soporta el pooler → SKU GP fijo (ADR-010 #2)

Opción B: Proxy separado con endpoints RW/RO

  • Descripción: Proxy administrado aparte (equivalente RDS Proxy) con endpoint read-only.
  • Paved Road: No
  • Tecnologías: proxy de base de datos separado
  • Esfuerzo estimado: 2 semanas
  • Riesgos: mínimo facturable propio que puede superar el ahorro; otro componente que operar

Opción C: Sin separación (todo al primary)

  • Descripción: Reportes y MCP contra el primary con throttling de aplicación.
  • Paved Road: No
  • Tecnologías: N/A
  • Esfuerzo estimado: 0 semanas
  • Riesgos: una consulta analítica pesada degrada el gobierno transaccional — inaceptable para el negocio

Paso 7: Decisión

Decisión Adoptada

Separación writer/reader con réplica de lectura y pooler integrado del servicio gestionado; MCP y reportería solo por la ruta read-only con credencial técnica exclusiva.

Razones Principales

  • Aislamiento de carga sin componente adicional que operar
  • Pooler integrado sin línea de costo separada (ADR-2026-106 de la propuesta Azure)
  • El aislamiento también es de seguridad (credencial read-only)

Consecuencias Positivas Esperadas

  • Reportes nunca degradan lo transaccional
  • Ráfagas serverless absorbidas por el pooler

Consecuencias Negativas Aceptadas

  • Lag de réplica < 30 s tolerado por reportes (monitoreado como NFR)
  • SKU fijo GP (sin tier Burstable) por requisito del pooler

Qué NO se Decidió

  • Proxy separado: costo fijo adicional sin beneficio sobre el integrado
  • Sin separación: riesgo operativo inaceptable

Paso 8: Re-evaluation Triggers

  • Saturación sostenida del primary pese al pooler (alerta SLO de capacidad, TD-SRE-01)
  • Que el servicio gestionado soporte Private Endpoints y cambie la topología de red

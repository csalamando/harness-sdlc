HU-001 — Crear y editar registros de catálogo con validación de llaves

Roles: ROL-02 (spec/roles.md) Épica: EP-01 | Prioridad: Must

Como Editor quiero crear y editar registros de cualquier catálogo (SN, ET, STI, APP, INT, ITSM y maestros) con validación de campos requeridos y llaves foráneas para mantener el inventario completo y referencialmente íntegro.

Criterios de aceptación (Gherkin)

Escenario: camino feliz — crear STI válido
  Dado que estoy autenticado con rol Editor
    Y existe la aplicación "APP-PORTAL" en estado distinto de "Retirada"
  Cuando creo un STI con nombreFuncional "Consulta Saldos", appProveedoraCodigo "APP-PORTAL" y criticidad "Alto"
  Entonces el STI queda persistido con ID asignado, fechaCreacion y usuarioCreacion
    Y queda registrado un evento "create" en el audit log

Escenario: error de validación — FK inexistente
  Dado que estoy autenticado con rol Editor
  Cuando intento crear un STI con appProveedoraCodigo "APP-NO-EXISTE"
  Entonces el sistema rechaza la operación con mensaje "La aplicación APP-NO-EXISTE no existe"
    Y no se persiste ningún cambio

Escenario: caso borde — app proveedora retirada
  Dado que la aplicación "APP-LEGACY" tiene cicloVidaCMDB "Retirada"
  Cuando intento crear un STI activo con appProveedoraCodigo "APP-LEGACY"
  Entonces el sistema rechaza la operación según BR-006 (regla DQ-010)

Reglas de negocio aplicables

BR-001, BR-002, BR-003, BR-006

Dependencias

HU-006 (RBAC define quién es Editor); fuente de verdad de SN/ET es EA (EP-07, Sprint 2) — en Sprint 1 la creación manual está permitida.

HU-003 — Autenticación corporativa y permisos por rol

HU-034 — Política maker-checker configurable por campo crítico y por catálogo (Sprint 12, CR-S12-MKCK)

Roles: ROL-02 (Editor), ROL-03 (Aprobador) (spec/roles.md)

Como gobernador del catálogo quiero que los cambios que tocan campos marcados como críticos en el diccionario —o cualquier cambio en catálogos declarados de gobierno estricto— generen automáticamente una solicitud de aprobación (HTTP 202) en lugar de persistir directo para que la regla BR-011 se cumpla de verdad: hoy toda alta/edición persiste directo ("Sprint 1: directo") y la bandeja de aprobaciones nunca recibe solicitudes reales.

Criterios de aceptación

Escenario: edición de campo crítico genera solicitud (no persiste)
  Dado que el diccionario de "aplicaciones" marca el campo "criticidad" como crítico
    Y existe el registro "APP-CORE" con criticidad "Bajo"
  Cuando un Editor actualiza "criticidad" a "Alto"
  Entonces la API responde 202 con la solicitud creada (id, operacion=update, cambio)
    Y el registro "APP-CORE" conserva criticidad "Bajo" (no se aplica hasta aprobar)
    Y la bandeja de Aprobaciones muestra la solicitud Pendiente con el diff campo a campo

Escenario: edición de campo NO crítico persiste directo
  Dado el mismo diccionario
  Cuando un Editor actualiza solo campos no críticos
  Entonces la API responde 200 y el cambio persiste de inmediato (comportamiento actual)

Escenario: aprobar una solicitud de update aplica el cambio
  Dada la solicitud Pendiente del primer escenario
  Cuando un Aprobador (distinto del solicitante, BR-010) la aprueba con comentario
  Entonces el registro refleja criticidad "Alto", la solicitud queda Aprobada y se audita (BR-012)

Escenario: aprobar una solicitud de create inserta el registro
  Dado que el catálogo "aplicaciones" está en la lista de gobierno estricto (MAKER_CHECKER_CATALOGS)
  Cuando un Editor crea un registro nuevo
  Entonces la API responde 202 y el registro NO existe todavía
    Y al aprobarse la solicitud (operacion=create) el registro se inserta con sus atributos
    Y al rechazarse no queda rastro del registro (solo la solicitud Rechazada y la auditoría)

Escenario: solicitud huérfana no se puede aprobar
  Dada una solicitud de update Pendiente cuyo registro fue eliminado después
  Cuando un Aprobador intenta aprobarla
  Entonces la API responde 409 (el cambio ya no tiene destino)

Política (configurable, sin cambio de esquema)

  • Nivel campo: un update cuyo diff toca al menos un campo con critical: true en el diccionario del catálogo → maker-checker. Resto → directo.
  • Nivel catálogo: la variable de configuración MAKER_CHECKER_CATALOGS (lista separada por comas, * = todos) fuerza maker-checker para create y update en esos catálogos, aunque no se toquen campos críticos.
  • delete (soft/hard) queda fuera de esta HU: sigue directo, restringido a admin (HU-007) y auditado.

Reglas de negocio aplicables

BR-010 (cuatro ojos), BR-011 (maker-checker), BR-012 (auditoría), BR-003 (campos críticos del diccionario), BR-018 (permiso por catálogo).

Dependencias

Infra de aprobaciones existente (HU-006: tabla aprobaciones, endpoints /api/approvals, decideApproval, bandeja UX-F3). Esta HU cierra el hueco de generación: los comentarios "Sprint 1: directo" de store.ts y catalogs-records.ts quedan superseded.

Como gobernador del catálogo quiero que al generarse una solicitud maker-checker se notifique en la campana a los usuarios con asignación vigente de approve sobre ese catálogo (BR-018), con una opción por asignación para activar/silenciar ese aviso, y que la pantalla Permisos muestre el correo/OID del usuario además de su nombre para que las solicitudes no dependan de que el aprobador revise la bandeja por iniciativa propia, y para saber con qué usuario (correo) debo iniciar sesión — hoy solo se ve el nombre y con varios usuarios de prueba del mismo nombre es ambiguo.

HU-036 — Política maker-checker administrable por catálogo desde la UI (Sprint 14 — propuesta)

Roles: ROL-04 (Administrador), ROL-03 (Aprobador), ROL-02 (Editor) (spec/roles.md)

Como administrador del catálogo (ROL-04 global o usuario con asignación de administración sobre ese catálogo, BR-018) quiero activar/desactivar la exigencia de aprobación por catálogo y elegir si aplica a todo el catálogo o campo a campo (marcando qué campos exigen aprobación), desde una pantalla de administración y con efecto inmediato para gobernar el maker-checker sin depender de un redeploy ni de editar la variable MAKER_CHECKER_CATALOGS de la Function App — hoy cambiar la política exige tocar configuración de infraestructura, lo que la hace inusable para los administradores funcionales.

Contexto y problema

HU-034 introdujo la política: nivel campo vía critical del diccionario y nivel catálogo vía MAKER_CHECKER_CATALOGS (env var). La env var es global a las 3 Function Apps, exige redeploy/ajuste de infra y no la puede operar un administrador funcional. Además el flag critical del diccionario mezcla dos preocupaciones: calidad de datos (DQ) y gobierno de cambios.

Criterios de aceptación

Escenario: activar aprobación para todo un catálogo
  Dado que soy administrador con permiso de administración sobre "regulaciones"
  Cuando en Administración → Política de aprobación selecciono "regulaciones", modo "Todo el catálogo" y guardo
  Entonces todo create/update posterior sobre "regulaciones" genera solicitud maker-checker (202)
    Y el cambio de política queda auditado (BR-012) con usuario, modo anterior y modo nuevo
    Y los otros workers lo aplican sin reinicio (refresco de gobierno, S2-9)

Escenario: política campo a campo
  Dado que "aplicaciones" está en modo "Campos seleccionados"
  Cuando marco "criticidad" y "datosPersonales" y desmarco "nombre"
  Entonces un update que solo cambia "nombre" persiste directo (200)
    Y un update que toca "criticidad" genera solicitud maker-checker (202)

Escenario: desactivar la política de un catálogo
  Dado que "proveedores" tiene modo "Todo el catálogo"
  Cuando cambio a "Sin aprobación" y guardo
  Entonces create/update sobre "proveedores" vuelven a ser directos
    Y las solicitudes ya pendientes NO se cancelan: siguen decidiéndose en la bandeja

Escenario: permiso insuficiente
  Dado que soy Editor (ROL-02) sin asignación de administración sobre "regulaciones"
  Cuando intento guardar la política de "regulaciones"
  Entonces recibo 403 y la política vigente no cambia

Escenario: precedencia y arranque
  Dado que existe política persistida en BD para un catálogo
  Entonces la BD manda sobre MAKER_CHECKER_CATALOGS
    Y si un catálogo no tiene fila en BD, aplica la env var como fallback de arranque (compatibilidad)

Reglas de negocio aplicables

BR-010 (cuatro ojos), BR-011 (maker-checker), BR-012 (auditoría), BR-018 (permiso por catálogo), SEC-004 (autorización server-side).

Decisiones de diseño propuestas (a validar en GATE 1)

  • Persistencia: tabla nueva politicas_aprobacion (migración V012): catalogo PK, modo (inactivo | campos_criticos | todo_catalogo), campos JSONB (lista de campos que exigen aprobación en modo campos_criticos), actualizado_por, fecha_actualizacion. ADR Tier 2 (afecta gobierno de cambios, no es PII).
  • Permiso: nuevo permiso de asignación manage-policy por catálogo (BR-018); ROL-04 global lo posee implícito. El permiso manage-grants existente NO lo incluye (separación: otorgar permisos ≠ definir gobierno de cambios).
  • Relación con critical del diccionario: el modo campos_criticos parte de los campos critical actuales como selección inicial, pero la lista editable pasa a vivir en la política; el flag del diccionario queda solo para DQ (una sola preocupación por artefacto). Transición: si el catálogo no tiene fila, se comporta como hoy.
  • Refresco: la política es dato de gobierno — viaja en refreshDiccionariosSiObsoleto (TTL 60 s + forzado), mismo patrón que diccionarios/grants/enum.
  • delete sigue fuera del maker-checker (HU-034): directo, solo admin, auditado.
  • Env var MAKER_CHECKER_CATALOGS: queda como fallback de arranque para catálogos sin fila en BD; se documenta como legado y su vaciado completo es el estado objetivo.

Dependencias

HU-034 (motor maker-checker), HU-035 (avisos a aprobadores), S2-9/TD-008 (refresco de gobierno y frescura de records). Pantalla nueva PANT-22 en spec/ux/screen-inventory.md.

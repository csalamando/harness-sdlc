Reglas de Negocio — Catálogo TI

Versión: 0.2 | Fecha: 2026-08-11 | Fuente: PoC CatalogoTI_V41 (diccionario de datos, motor DQ, aprobaciones) + AWS.txt

IDReglaFuente
BR-001Todo registro tiene PK única por catálogo: SN/ET/STI usan ID tipo {PREFIX}-{GUID} (el GUID de EA es la llave de conciliación); APP/INT/maestros usan código corto. Las PK no se reutilizan.PoC §Modelo de datos; ADR-005 PoC
BR-002Toda FK debe apuntar a un registro existente y no eliminado físicamente. La creación/edición valida la FK en el momento de persistir.PoC (validación FK)
BR-003Cada catálogo define campos críticos (diccionario de datos); un registro con campos críticos vacíos aparece en "Pendientes". Ej.: SN sin responsables/owners/canal; STI sin nombreTecnico/autenticacion/clasifDatos/appProveedora; APP sin stack/tipoArquitectura; INT sin origen; ITSM sin SLA.PoC renderPendientes + DD
BR-004La cadena de trazabilidad canónica es: Macroproceso → SN → Etapa · STI → Integración → Aplicación → BD, con ITSM transversal. Las relaciones SN↔STI viven en la tabla puente relaciones; APP↔BD en bdAppRel; consumidores de STI se derivan de integraciones.serviciosTIUsados.PoC §5 Trazabilidad
BR-005Una FK que apunta a un código inexistente es una "llave rota": se reporta en la vista homónima y en badges; la meta es 0. El hard-delete limpia las FKs afectadas y audita el conteo.PoC Llaves Rotas
BR-006Un STI activo no puede tener como app proveedora una aplicación en estado "Retirada" (DQ-010). Apps con BIA=SI deben tener RTO, RPO y plan DRP (DQ-001/002/003). STI con clasifDatos=Confidencial requiere cifrado (DQ-004); con Restringido no admite autenticación Basic (DQ-005). Integración tipo API requiere al menos un STI (DQ-006). ITSM debe tener SLA (DQ-008) y cumplimiento ≥ 85 % (DQ-009). EOL de fabricante no puede estar vencido ni a <365 días sin tratamiento (DQ-007).PoC cat_reglasCalidad.js
BR-007RBAC con 4 roles: Lector (consulta), Editor (crea/edita, no elimina, no aprueba), Aprobador (edita y aprueba, no elimina), Admin (todo, incl. reglas DQ). Los roles se mapean a App Roles de Entra ID; sin token válido no hay acceso.PoC ROLE_PERMS + ADR-001
BR-008Toda llamada a API se autoriza con validación PoP/SHR; los intentos fallidos se registran en auditoría de seguridad.AWS.txt §3.1
BR-009(v2 — supersedes 2026-08-21, CR S11-Reuso, opción A aprobada por PO) El score de reuso de un STI = # apps consumidoras (appsConsumenCodigos) + # SN relacionados (relaciones) + factor de criticidad (Alto=3, Medio=2, Bajo=1). Las integraciones (serviciosTIUsados) suman como evidencia adicional cuando existen. STI huérfano = sin apps consumidoras, sin SN relacionados y sin INT que lo use; score ≥3 (sin contar criticidad) = alto reuso. La versión anterior (#INT + #SN + criticidad) queda como histórico: la fuente INT está sub-poblada (4 registros vs 575 STI con consumidoras).PoC renderReuso + decisión PO 2026-08-21
BR-019Integraciones sin STI (CR S11-INT, opción 1 aprobada por PO 2026-08-21): el catálogo integraciones se reserva para flujos sin servicio de por medio (ETL/Batch, Replicación BD, Archivo Plano y similares). Los flujos vía API/SOAP/Pub-Sub se derivan del catálogo de Servicios TI (appProveedoraCodigo → appsConsumenCodigos); no se crean registros INT redundantes para esos pares. Trazabilidad, impacto, mapa de relaciones y reuso recorren ambos caminos: INT explícitas y el derivado STI. Regla DQ asociada: una INT cuyo tipo es API/SOAP/Pub-Sub debe tener serviciosTIUsados poblado (DQ-006 ya existente se mantiene).Decisión PO 2026-08-21
BR-010Todo cambio auditable registra: fecha, usuario (identidad corporativa), rol, acción (create/update/approve/reject/soft-delete/hard-delete/import), catálogo, PK del registro y detalles.PoC logAudit
BR-011Los cambios críticos pasan por maker-checker: el cambio queda "Pendiente" con diff campo a campo hasta que un Aprobador lo aprueba (se aplica) o rechaza (se preserva el original). Toda aprobación admite comentario y delegación. El solicitante no puede aprobar su propio cambio.PoC Aprobaciones v15
BR-012Retención: audit log en caliente = últimos 5.000 eventos; el excedente se archiva. Cada registro conserva historial de cambios con hash de integridad; el soft-delete conserva historial completo.PoC (límite 5000, recordHash)
BR-013SLA de corrección DQ por criticidad: Alto=7 días, Medio=30 días, Bajo=90 días. Revisiones periódicas por criticidad del registro: Alto=3 meses, Medio=6 meses, Bajo=12 meses (fechaProximaRevision calculada).PoC DD + renderRevisiones
BR-014Importación Excel: las filas se validan con las mismas reglas del CRUD (BR-001/002/003). Política de atomicidad por definir en refinamiento (parcial con reporte vs. todo-o-nada); la plantilla vigente es la única estructura aceptada.PoC Importar/Exportar
BR-015La clasificación de datos (Público/Interno/Confidencial/Restringido) gobierna exportación y acceso MCP: el MCP solo lee vistas autorizadas con credencial técnica exclusiva y sin escritura. Exportaciones masivas de campos Confidencial/Restringido pueden restringirse por rol (decisión de Seguridad en Fase 2).PoC DD + AWS.txt §2.3
BR-016Renombrar la PK de un registro propaga el cambio a todas las FK que lo referencian (en todos los catálogos y tablas puente), en una sola transacción, y audita el conteo de referencias actualizadas. Si alguna propagación falla, todo se revierte.PoC updateReferencesOnKeyChange; gap-analysis §2.4
BR-017Nombres por encima de IDs/GUIDs: en todas las vistas (listas, FKs, fichas, trazabilidad, mapa, notificaciones) se muestra primero el nombre del registro; el ID/GUID es secundario u oculto porque no aporta valor al usuario final. Excepción: aplicaciones.codigo — el código de aplicación sí es valioso, fácil de leer y recordar (no es GUID), y se muestra con igual jerarquía que el nombre.Lineamiento PO 2026-08-12 (CR S3-UX); PoC v35 "IDs/GUIDs ocultos transversal"
BR-018RBAC granular por catálogo (CR S4-RBAC, opción B aprobada por PO 2026-08-13): el App Role de Entra define el rol base (techo global, BR-007); sobre él, la tabla asignaciones_catalogo (V007) otorga permisos adicionales por catálogo (edit/delete/approve) y el permiso manage-grants. Permiso efectivo = rol base OR asignación vigente; una asignación amplía, nunca reduce lo que el rol base ya otorga. Un usuario con rol base Lector puede ser editor de catálogos específicos. Nadie otorga permisos que no posee; manage-grants habilita administrar asignaciones solo de los catálogos donde se posee ese permiso (delegación); catalogo='*' está reservado al admin global. La lectura sigue global para todo usuario autenticado. Todo grant/revoke se audita (BR-010) con acciones grant/revoke. La autorización granular se resuelve siempre server-side (SEC-004); el JWT solo transporta identidad y rol base.CR S4-RBAC (PO 2026-08-13)

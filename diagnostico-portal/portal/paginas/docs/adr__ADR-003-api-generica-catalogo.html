Paso 1: Problem Statement

La entidad gobierna 13 catálogos con operaciones homogéneas (crear, leer, actualizar, validar referencias), pero también tiene capacidades de dominio diferenciadas (trazabilidad, impacto, aprobaciones, calidad de datos). Escribir un controlador por entidad multiplica código duplicado y hace costoso añadir un catálogo nuevo; tratar todo como genérico ahogaría la lógica de dominio.

Paso 4: Opciones Consideradas

Opción A: Controlador genérico /catalogs/{catalog}/... + servicios de dominio

  • Descripción: CRUD/listados genéricos gobernados por el diccionario de datos; endpoints específicos para trazabilidad, impacto, aprobaciones, DQ, auditoría y bulk.
  • Paved Road: Sí
  • Tecnologías: Azure Functions, Node.js/TypeScript
  • Esfuerzo estimado: 2 semanas
  • Riesgos: exige diccionario de datos fuerte y validación declarativa (riesgo controlado: el diccionario ya es artefacto gobernado)

Opción B: Un recurso REST por entidad

  • Descripción: 13 controladores específicos.
  • Paved Road: No
  • Tecnologías: Azure Functions, Node.js/TypeScript
  • Esfuerzo estimado: 5 semanas
  • Riesgos: duplicación masiva; cada catálogo nuevo repite el patrón completo

Paso 7: Decisión

Decisión Adoptada

API genérica por catálogo para CRUD/listados gobernada por el diccionario de datos, con endpoints específicos para las capacidades de dominio.

Razones Principales

  • Contrato estable al añadir catálogos (cero breaking changes)
  • Menos código duplicado
  • La lógica de dominio conserva endpoints propios y expresivos

Consecuencias Positivas Esperadas

  • Catálogos nuevos se habilitan por configuración/datos
  • Un solo punto de validación y auditoría de CRUD

Consecuencias Negativas Aceptadas

  • El diccionario de datos se vuelve punto crítico único (mitigado: artefacto gobernado con recibo)

Qué NO se Decidió

  • Controlador por entidad: costo lineal por catálogo sin beneficio de expresividad

Paso 8: Re-evaluation Triggers

  • Un catálogo con reglas de escritura tan particulares que el genérico no las exprese (candidato a endpoint de dominio)
  • Fecha de revisión programada: 2027-02-01

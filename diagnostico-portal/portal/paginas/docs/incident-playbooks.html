PB-01 — Errores 5xx sostenidos en API (alerta alert-5xx-*-prd, sev 2)

  • Confirmar en App Insights: endpoint afectado, excepciones dominantes (últimos 30 min).
  • Si coincide con un despliegue reciente → rollback inmediato con spec/runbook-deploy-rollback.md (slots/swap o redeploy del artefacto anterior).
  • Si no hay despliegue: revisar dependencias en orden — PostgreSQL (PB-04), APIM/WAF, identidad MSAL.
  • Mitigar: si un catálogo concreto falla por datos corruptos en última importación, restaurar versión previa (soft-delete BR-012 permite recuperación).
  • Escalar a sev-1 si > 50 % de requests fallan en horario hábil.
  • Al resolver: postmortem si fue sev-1/sev-2; verificar que alert-5xx vuelve a verde 2 ventanas seguidas.

PB-02 — Latencia p95 degradada (alerta alert-latencia-*-prd, sev 3)

  • Identificar endpoint en App Insights → Performance; distinguir operación normal (< 2 s) vs trazabilidad transitiva (< 5 s).
  • Si es trazabilidad/impacto: revisar profundidad del grafo solicitado; verificar índices de tablas de relaciones (V002) y plan de consulta en PostgreSQL.
  • Si es general: revisar cpu_percent/métricas del flexible server y cold starts del plan Flex Consumption.
  • Si correlaciona con importación masiva en curso → throttling: pausar importaciones (las reinicia el job, son idempotentes).
  • Persistente > 1 día hábil: elevar a Architect con propuesta (índice, caché de consulta, o ajuste de SLO en revisión mensual).

PB-03 — Fallos de importación masiva XLSX (sev 3; alerta pendiente TD-SRE-01)

  • Reproducir con el archivo del usuario (parser frontend/src/app/core/xlsx-parser.ts; firma PK/CFB y coerción de llaves documentadas).
  • Clasificar: error de formato (devolver al usuario con reporte de validación) vs error de plataforma (bug → hotfix con TDD).
  • Si > 5 % de jobs fallan en el día: suspender comunicación de nuevas cargas y revisar reglas de calidad activas.
  • Registrar patrón nuevo de fallo como regla de validación adicional (backlog BA).

PB-04 — Capacidad / degradación PostgreSQL (sev 4 preventiva, sev 2 si hay impacto)

  • Verificar cpu_percent, memory_percent, active_connections (límite vía PgBouncer :6432) y storage_percent.
  • Conexiones agotadas → confirmar que el backend usa pool PgBouncer (pool.ts); reiniciar Function App si hay fugas de conexión.
  • CPU/memoria > 80 % sostenido → escalar SKU del flexible server (terraform var.postgres_sku, ventana acordada; cambio con delta-spec si altera costo NFR §6).
  • Storage > 85 % → ampliar storage_mb (online, sin downtime).
  • Réplica de lectura habilitada → desviar consultas de trazabilidad pesada al reader.

PB-05 — Pérdida de datos / DR (sev-1; SLO RTO/RPO POR DEFINIR — riesgo O-1)

  • Activar restauración desde backup automatizado del flexible server (propuesta RPO 15 min — point-in-time restore).
  • Declarar incidente sev-1, congelar despliegues.
  • Restaurar a nuevo servidor y repuntar DNS privado / cadena de conexión (Key Vault secret), nunca sobrescribir el servidor afectado hasta preservar evidencia.
  • Validar integridad: conteos por catálogo vs última auditoría de exportación.
  • Postmortem obligatorio + revisión de RTO/RPO con negocio (desbloquea riesgo O-1).

Gestión del ciclo

Detectar (alerta Azure Monitor → action group) → Mitigar (playbook) → Resolver → Postmortem sin culpables (spec/templates/postmortem.md, sev-1/sev-2 en < 5 días) → Acciones correctivas al backlog del PO con ID.

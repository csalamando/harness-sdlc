ADR-001 — Identidad con Microsoft Entra ID + PoP/SHR

  • Estado: Aceptada (heredada de la PoC, ADR-001 original)
  • Fecha: 2026-08-08 (consolidación)
  • Contexto: La organización opera Microsoft 365/Entra ID; la PoC simula roles con un selector local (gap C-3). Duplicar directorio (Cognito u otro IdP) contradice el lineamiento.
  • Opciones: Entra ID | Cognito | Directorio propio.
  • Decisión: Entra ID como única fuente de identidad; App Roles (Lector/Editor/Aprobador/Admin) mapean el RBAC (BR-007); cada llamada a API valida token + prueba PoP/SHR (BR-008) mediante authorizer dedicado. MSAL en el front.
  • Consecuencias: MFA y Acceso Condicional heredados; ningún despliegue compartido antes de EP-02; IAM Identity Center solo para devs/ops (si AWS).

ADR-002 — Front-end Angular v17+

  • Estado: Aceptada (heredada de la PoC, ADR-008 original)
  • Contexto: Estándar corporativo de front; la PoC vanilla solo validó modelo y UX.
  • Decisión: Angular v17+ standalone, Signals, MSAL + interceptor JWT, lazy loading por catálogo; tokens desde spec/tokens.json (Style Dictionary); tests Jasmine/Karma + Playwright.
  • Consecuencias: Tipado fuerte del modelo en compilación; esfuerzo de reescritura (la PoC no se reutiliza como código); cadena de build Node en CI/CD.

ADR-003 — API REST genérica por catálogo

  • Estado: Propuesta
  • Contexto: 13 catálogos con CRUD homogéneo (validación FK + diccionario de datos) y un núcleo de dominio diferenciado (trazabilidad, DQ, gobierno).
  • Opciones: Un recurso REST por entidad | controlador genérico /catalogs/{catalog}/... + servicios de dominio.
  • Decisión: API genérica por catálogo para CRUD/listados, con esquemas gobernados por el diccionario de datos; endpoints específicos para trazabilidad, impacto, aprobaciones, DQ, auditoría y bulk.
  • Consecuencias: Menos código duplicado y contrato estable al añadir catálogos; exige diccionario de datos fuerte y validación declarativa.

ADR-004 — Base relacional PostgreSQL con FK reales

  • Estado: Aceptada (2026-08-08): excepción PostgreSQL aprobada por el dueño frente al lineamiento Oracle (C-2 resuelto)
  • Contexto: N relaciones N:N, integridad referencial, conciliación por GUID. DynamoDB/NoSQL descartado (PoC ADR-003).
  • Decisión: PostgreSQL gestionado (Aurora Serverless v2 si AWS / Azure Database for PostgreSQL si Azure) con FK constraints reales y tablas puente.
  • Consecuencias: Integridad en base (BR-002); excepción formal aprobada 2026-08-08 — la brecha de catálogo tecnológico queda cubierta; mantener plan de reversibilidad documentado.

ADR-005 — Nube destino: AWS serverless vs Azure

  • Estado: Aceptada (2026-08-08): Opción B — Azure (C-1 resuelto por decisión humana del dueño del producto)
  • Contexto: AWS.txt (v2.2, 5-ago-2026) propone AWS serverless; AZURE.txt (v1.0, 5-ago-2026) documenta la alternativa Azure equivalente. La vista de arquitectura de la PoC (ADR-009 original) marca Azure preferente porque EA (SQL Server) y Entra ID ya están en Azure (evita egress cross-cloud, ingesta/MCP co-localizados en la misma VNet, identidad nativa).
  • Opciones:
  • A) AWS (AWS.txt v2.2): Amplify + CloudFront/WAF + API Gateway HTTP API + Lambda + Step Functions + Aurora Serverless v2 (writer+reader, 1-4 ACU) + RDS Proxy (endpoints RW/RO) + Secrets Manager/KMS + CloudWatch/GuardDuty/Security Hub. Autorización PoP/SHR con Lambda REQUEST Authorizer. USD 356,05/mes técnico — USD 445,06/mes con reserva FinOps 25 %.
  • B) Azure (AZURE.txt v1.0): Static Web Apps + WAF corporativo compartido + APIM Premium corporativo (reutilizado, coste incremental cero) + Functions Flex Consumption + Durable Functions + PostgreSQL Flexible Server GP D2ds v5 (primary + read replica) + PgBouncer integrado (sin proxy separado) + Key Vault + Monitor/App Insights + Defender for Cloud. Identidad Entra ID OAuth 2.0 validada en APIM. USD 285,88/mes técnico — USD 357,35/mes con reserva FinOps 25 %.
  • Comparativa clave:
  • Coste: Azure ≈ 20 % más barato (357 vs 445 USD/mes presupuesto), apalancado en capacidad corporativa ya contratada (WAF y APIM a coste incremental cero — pendiente validación del custodio, ADR-2026-102/103).
  • Identidad: AWS exige Lambda Authorizer PoP/SHR propio; Azure valida OAuth 2.0 nativamente en APIM (menos código de seguridad propio; verificar equivalencia PoP/SHR con Seguridad).
  • Ingesta EA: en Azure, EA (SQL Server) y el MCP co-localizan en la misma nube/VNet; en AWS requiere VPN/Direct Connect y egress cross-cloud.
  • Elasticidad BD: Aurora escala 1-4 ACU automático; Flexible Server D2ds v5 es tamaño fijo 2 vCores (cambio de tier manual).
  • Pool: RDS Proxy con mínimo facturable 8 ACU (coste propio y riesgo de que supere el ahorro serverless) vs. PgBouncer integrado sin línea de coste.
  • Dependencias compartidas (Azure): onboarding formal al WAF y APIM corporativos (capacidad, cuotas, red, SLA) antes del ARB; arranque en frío de Flex Consumption (mitigable con Always Ready).
  • Madurez documental: AWS v2.2 con ADRs 2026-001..006 y pricing detallado; Azure v1.0 con ADRs 2026-101..107, participantes ARB pendientes. Inconsistencia menor detectada en AZURE.txt §3 ("APIM Consumption" en la tabla de controles vs. Premium corporativo en el resto del documento) — aclarar con el autor.
  • Común a ambas: excepción PostgreSQL pendiente (C-2), pricing por validar en calculadora oficial, RTO/RPO por definir (O-1).
  • Decisión: AZURE (Opción B), aprobada por el dueño el 2026-08-08. Factores decisivos: coste −20 % (USD 357 vs 445/mes), reutilización de WAF/APIM corporativos, identidad nativa en APIM, ingesta EA co-localizada, PgBouncer sin coste separado. Acciones derivadas: onboarding formal al WAF y APIM corporativos antes del ARB (ADR-2026-102/103), prueba de carga con arranque en frío (Always Ready si aplica), aclarar inconsistencia "APIM Consumption vs Premium" en AZURE.txt §3. La alternativa AWS (AWS.txt v2.2) queda como referencia histórica.
  • Consecuencias: Infraestructura, pipelines y GATE 3 se construyen sobre Azure (AZURE.txt v1.0 como baseline). Dependencias compartidas (WAF/APIM) se gestionan con los equipos custodios. La spec de dominio y API no cambia.

ADR-006 — Separación writer/reader con pool de conexiones

  • Estado: Aceptada (Azure: PgBouncer integrado en primary y read replica, ADR-2026-106)
  • Contexto: Reportería y MCP no deben impactar lo transaccional; las funciones serverless generan ráfagas de conexiones.
  • Decisión: Réplica de lectura + pool (RDS Proxy con endpoint read-only si AWS; equivalente gestionado si Azure). MCP y reportería solo por la ruta read-only con credencial técnica exclusiva (BR-015).
  • Consecuencias: Aislamiento de carga; coste fijo adicional (mínimo facturable del proxy — mitigar con prueba de carga y revisión de Aurora provisionado si la carga es estable); posible lag < 30 s tolerado por reportes.

ADR-007 — Ingesta EA por watermark, idempotente por GUID

  • Estado: Aceptada (heredada de la PoC, ADR-002/005 originales)
  • Decisión: Delta por ModifiedDate (watermark), conciliación por GUID de EA en tagged values + tabla key_mappings como fallback. Proceso idempotente y re-ejecutable. Evolución futura a Change Tracking si se requiere detectar borrados (EP-14, Won't este ciclo).
  • Consecuencias: Cero doble digitación; borrados sin reconciliación periódica (trade-off aceptado).

ADR-008 — Soft-delete por defecto

  • Estado: Aceptada (BR-012, heredada PoC ADR-007)
  • Decisión: Toda baja es soft-delete (activo=false, conserva historial). Hard-delete solo Admin, doble confirmación, limpieza transaccional de FKs auditada.
  • Consecuencias: Evidencia histórica preservada (regulatorio); consultas filtran activo=true por defecto; llaves rotas solo pueden venir de hard-delete histórico o cargas externas.

ADR-009 — Infraestructura como código con Terraform

  • Estado: Aceptada (2026-08-08, decisión del dueño en Fase 6)
  • Contexto: La arquitectura aprobada (ADR-005, baseline AZURE.txt v1.0) define los servicios Azure pero no la herramienta de aprovisionamiento. Se requiere IaC repetible para dev/staging/PRD con revisión en PR y estado versionado.
  • Opciones: Bicep | Terraform | ARM templates | aprovisionamiento manual.
  • Decisión: Terraform (provider azurerm ~> 4.x) como única herramienta IaC del proyecto. Estado remoto en Azure Storage Account dedicado (tfstate) con bloqueo; un root module plano con tfvars por entorno (dev/staging/prd); terraform plan obligatorio en PR y apply solo desde pipeline con aprobación de entorno.
  • Consecuencias: Portabilidad del conocimiento (el equipo ya opera Terraform en otros dominios), estado explícito y bloqueado, plan revisable antes del ARB; a cambio, se gestiona el ciclo de vida del provider y del backend de estado. Los recursos corporativos compartidos (APIM Premium, WAF) NO se crean con Terraform: se referencian como data/variables tras el onboarding con el custodio.

ADR-010 — Lecciones verificadas del primer despliegue dev (2026-08-11)

  • Estado: Aceptada (supersedes parciales de AZURE.txt §2.1 donde el entorno real contradijo el diseño)
  • Contexto: El primer terraform apply real sobre la suscripción dev (eastus inicialmente) destapó 10 restricciones del entorno que el diseño en papel no podía conocer. Se registran como decisiones operativas permanentes.
  • Decisiones:
  • Región dev = eastus2: eastus no tiene oferta de PostgreSQL Flexible Server en esta suscripción (capabilities [] verificado con az rest). SWA tampoco existe en eastus; ambos quedan en eastus2.
  • SKU PostgreSQL dev = GP_Standard_D2ds_v5 (igual que staging/prd): el tier Burstable NO soporta PgBouncer integrado; ahorrar con B1ms implicaría renunciar al pooler (ADR-006).
  • PostgreSQL Flexible sin Private Endpoints: el servicio no soporta PE; la red privada es por integración VNet delegada (Microsoft.DBforPostgreSQL/flexibleServers), no por pep-psql.
  • Un plan FC1 por Function App: Flex Consumption solo admite UN site por plan — 3 planes asp-*-{crud,gobierno,bulk-ingesta}.
  • Alertas por scheduled query KQL sobre App Insights: FC1 no emite las métricas de plataforma Http5xx/HttpResponseTime (ver spec/slo.md §2).
  • Migraciones embebidas en el arranque del store (PG_AUTO_MIGRATE, advisory lock 727272): la BD solo es alcanzable desde la VNet; Flyway externo sigue siendo la vía formal de PRD (data-governance.md).
  • SPA consume la API por URL absoluta (environment.prod.ts → func-...-crud.azurewebsites.net, CORS limitado al host SWA): las 3 Function Apps reciben el mismo paquete completo; en staging/prd la base será APIM (ADR-005). El 404 inicial de /api relativo quedó documentado.
  • Entra ID emite tokens v1 por defecto (requestedAccessTokenVersion sin definir): el verificador del backend acepta v1 (issuer sts.windows.net, aud api://<clientId>, usuario en upn/unique_name) y v2. Los App Roles viajan en el access token, nunca en el idToken (SEC-001).
  • Angular AOT: no usar ?? en el track de un @for (bug del compilador en build optimizado: tmp_N_0 is not defined, pantalla en blanco solo en producción).
  • Consecuencias: dev quedó operativo (apply + deploy + login Entra ID + CRUD persistido, smoke verde 2026-08-11). Estas restricciones aplican igual a staging/prd y ya están codificadas en infra/terraform/.

ADR-011 — Bootstrap idempotente del rol catalogo_app en el arranque del backend (CR-S6-RBAC-DB)

  • Estado: Aceptada (aprobada por el dueño 2026-08-20) · Relación: supersedes la ejecución manual pendiente de S2-8 (infra/scripts/crear-usuario-catalogo-app.sql queda como referencia histórica).
  • Risk Tier: 1 (toca autenticación y datos) — Advice Process: Security (SEC-013) + Data Engineer.
  • Contexto: En Sprint 5 (hardening S2-8) infra/terraform/compute.tf fijó PG_USER=catalogo_app, pero el rol nunca se creó en el servidor (paso manual pendiente). El 2026-08-20 un CD manual corrió terraform apply y aplicó el setting → todos los endpoints devolvieron 500 ("given role does not exist", pg-pool → runMigrations). La recuperación inmediata fue revertir PG_USER al login admin via app settings. Además se verificó que terraform NO puede gestionar el rol (provider postgresql requiere acceso directo a 5432 y el servidor tiene publicNetworkAccess=Disabled; los runners de GitHub están fuera de la VNet).
  • Decisión:
  • El rol se auto-provisiona por código, no por CLI ni por terraform. Al crear el store PG, si el login como catalogo_app falla con "role does not exist", el backend abre UNA conexión como admin (credenciales ya en Key Vault: postgres-admin-password) y ejecuta de forma idempotente (IF NOT EXISTS): CREATE ROLE catalogo_app LOGIN, REVOKE ALL ON SCHEMA public, GRANT USAGE, CREATE ON SCHEMA public, GRANT SELECT/INSERT/UPDATE/DELETE ON ALL TABLES, ALTER DEFAULT PRIVILEGES. Corre dentro de la Function (integrada a la VNet), por lo que no requiere abrir la red.
  • GRANT CREATE ON SCHEMA public se concede porque runMigrations corre embebido con el mismo usuario y CREATE TABLE IF NOT EXISTS exige CREATE aunque la tabla exista. Deuda registrada: separar un usuario de migraciones con DDL y dejar catalogo_app 100% DML (refina SEC-013).
  • El script infra/scripts/crear-usuario-catalogo-app.sql queda como documentación; la fuente de verdad es el bootstrap en backend/src/db/.
  • TDD: tests Vitest con pg-mem/mock que verifican (a) bootstrap se dispara solo ante "role does not exist", (b) idempotencia (segundo arranque no re-crea), (c) fallo distinto (ej. password errada) NO dispara bootstrap y propaga el error.
  • Consecuencias: cualquier entorno nuevo (staging/prd) se auto-aprovisiona sin pasos manuales; se elimina la clase de error "apply cambia PG_USER sin que el rol exista"; el drift terraform/CLI desaparece para este recurso. GATE 2.5: sin hallazgos nuevos (la conexión admin de bootstrap usa el secreto ya existente en KV, no uno nuevo).

ADR-012 — Listas de valores enum administrables con borrado lógico (HU-029, Sprint 9)

  • Estado: Aceptada (aprobada por el dueño 2026-08-20 con el plan Sprint 9) · Relación: aditiva.
  • Risk Tier: 2 (toca modelo de datos y permisos; no auth ni PII) — Advice Process: Data Engineer (migración V009) + Security (reutiliza RBAC por catálogo, SEC-021).
  • Contexto: Los valores de los campos enum viven hoy en diccionarios.enum_values (JSONB) y solo cambian por seed/despliegue. El dueño requiere que los dueños de cada catálogo los administren desde el front, con borrado lógico para no romper registros existentes, y que los booleanos Sí/No se editen con radio buttons.
  • Decisión:
  • Tabla nueva enum_valores (catalogo, campo, valor, activo, fecha_baja, usuario_baja) (V009) en lugar de editar el JSONB: permite borrado lógico por valor, auditoría por fila y reactivación. diccionarios.enum_values queda como fallback/semilla — si un (catálogo, campo) no tiene filas en enum_valores, se usan los valores del diccionario base (todos activos). Fuente efectiva = enum_valores cuando existe.
  • Permiso = grant de edición sobre el catálogo (RBAC granular S4, BR-018): quien edita el catálogo administra sus listas. No se crea un rol nuevo.
  • Validación de escritura relajada: un registro puede conservar un valor enum inactivo (borrado lógico no invalida lo existente; DQ no lo marca). La validación solo exige que el valor exista (activo o inactivo) — nunca se aceptan valores fuera de la unión conocida, salvo fkLenient que ya tiene su propia regla.
  • Administrador inline en el modal de edición (⚙ junto al campo enum), decisión del dueño; no página separada.
  • Booleanos: enum cuyos valores activos son exactamente Sí/No → radio group en el formulario.
  • TDD: Vitest (endpoints, borrado lógico, 403, valor inactivo conservado) + Karma (⚙ visible solo con permiso, radio Sí/No, refresco inmediato).
  • Consecuencias: las listas se gobiernan sin despliegues; el seed dictionaries.json sigue siendo la semilla inicial; un futuro administrador de colDefault (UX-F22) puede seguir el mismo patrón. Deuda: el diccionario base y enum_valores pueden divergir — el reporte DQ podría listar valores huérfanos en una iteración futura.

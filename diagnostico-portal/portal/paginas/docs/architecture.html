3.1 Topología de Function Apps: responsabilidades, estado actual y split vía APIM

¿Por qué 3 Function Apps y no 1?

No son redundantes: el split busca aislamiento de cargas y escalado independiente en Flex Consumption. Una ingesta masiva de EA o una consulta de impacto de grafos no debe competir por cómputo (ni por presupuesto de escalado) con el CRUD interactivo de los usuarios. Cada app tiene su propio plan, sus propios límites de escalado y su propia observabilidad.

Estado actual (agosto 2026) — split inactivo por diseño, no por accidente

  • El CD despliega el mismo paquete a las 3 apps (cd.yml): todas registran las 41 funciones (main: dist/src/functions/*.js). Mantener un solo artefacto simplifica el pipeline mientras no hay routing.
  • La SPA apunta directo a crud (frontend/src/environments/environment.prod.ts); gobierno y bulk-ingesta están desplegadas pero sin tráfico — réplicas latentes listas para el split.
  • APIM corporativo no integrado aún: pendiente onboarding con el custodio (security.tf, variables corporate_apim_name/corporate_apim_rg vacías).
  • ⚠️ Consecuencia operativa: una llamada a un endpoint de "gobierno" contra la app crud funciona hoy. Tras activar APIM, el path manda y llamar al host equivocado quedará bloqueado por red (acceso público restringido en staging/prd).

Diseño futuro con APIM Premium corporativo (ADR-2026-103 / ADR-005)

1. Estructura en APIM — un solo API lógico catalogo-ti-api (por ambiente), con las operaciones agrupadas por path y 3 backends (cati-crud-{env}, cati-gobierno-{env}, cati-bulk-{env}) apuntando al host name de cada Function App. Las Function Apps quedan con acceso público deshabilitado (solo VNet/APIM vía private endpoint).

3. Política global (API-level) — validación JWT + routing por path. El backend nunca confía en el edge: la validación de rol por App Role se mantiene en las funciones (defensa en profundidad, BR-007); APIM valida firma/emisor/audiencia/expiración y enruta:

<policies>
  <inbound>
    <base />
    <!-- SEC-002: JWT Entra ID v2 — firma, emisor, audiencia y expiración -->
    <validate-jwt header-name="Authorization" failed-validation-httpcode="401"
                  failed-validation-error-message="Token ausente, expirado o inválido"
                  require-expiration-time="true" require-signed-tokens="true">
      <openid-config url="https://login.microsoftonline.com/{{cati-entra-tenant-id}}/v2.0/.well-known/openid-configuration" />
      <issuers>
        <issuer>https://login.microsoftonline.com/{{cati-entra-tenant-id}}/v2.0</issuer>
      </issuers>
      <audiences>
        <audience>{{cati-api-client-id}}</audience>
      </audiences>
      <required-claims>
        <claim name="scp" match="any" separator=" ">
          <value>access_as_user</value>
        </claim>
      </required-claims>
    </validate-jwt>
    <!-- Routing por path hacia la Function App responsable -->
    <choose>
      <when condition="@(context.Request.Url.Path.StartsWith(&quot;/api/bulk/&quot;))">
        <set-backend-service base-url="{{cati-backend-bulk-url}}" />
      </when>
      <when condition="@(context.Request.Url.Path.StartsWith(&quot;/api/catalogs&quot;) || context.Request.Url.Path.StartsWith(&quot;/api/dictionaries&quot;))">
        <set-backend-service base-url="{{cati-backend-crud-url}}" />
      </when>
      <otherwise>
        <set-backend-service base-url="{{cati-backend-gobierno-url}}" />
      </otherwise>
    </choose>
    <!-- Cuota justa por usuario (PoC: generoso; ajustar tras telemetría) -->
    <rate-limit-by-key calls="600" renewal-period="60"
        counter-key="@(context.Request.Headers.GetValueOrDefault(&quot;Authorization&quot;,&quot;anon&quot;))" />
  </inbound>
  <backend><base /></backend>
  <outbound><base /></outbound>
  <on-error><base /></on-error>
</policies>

Notas de diseño:

  • Defensa en profundidad: aunque APIM valide el JWT, las funciones siguen validando firma/roles localmente (ADR-005, SEC-002) — requisito mientras dev expone las apps directamente, y salvaguarda si el edge cambia.
  • PoP/SHR (SEC-002): la política validate-jwt evoluciona a token proof-of-possession cuando el custodio lo habilite; hoy queda como bearer + scope.
  • CORS no se configura en APIM: la SPA llega same-origin a través del WAF corporativo (/ → SWA, /api/ → APIM); CORS solo aplica si se habilita un origen cruzado nuevo.
  • environment.prod.ts cambia apiBase a la URL de APIM; las 3 apps dejan de recibir tráfico directo y su acceso público se restringe (ya previsto en compute.tf para staging/prd).
  • Ingesta EA seguirá llegando a bulk-ingesta por VNet (no por APIM) cuando se automatice.

7. Patrones

  • Idempotencia en ingesta y en mutaciones reintentables (GUID EA + claves de idempotencia).
  • CQRS ligero: escrituras al writer; reportería, dashboards, trazabilidad pesada y MCP al reader.
  • Outbox/audit transversal: toda mutación emite evento audit (BR-010).
  • Contrato primero: el front se genera contra api-contract.yaml; mocks MSW para desarrollo paralelo.

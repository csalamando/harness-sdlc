2. Deploy

2.1 staging (automático tras CI verde en master)

  • CI verde (tsc, 102 Vitest, 35/36 Cucumber, 17 Karma, terraform validate).
  • CD job staging: terraform plan -var-file=environments/staging.tfvars → apply → deploy 3 Function Apps → deploy SWA → smoke test (/api/catalogs/aplicaciones/records responde 200).
  • Verificación manual GATE 3 en staging:
  • [ ] Login Entra ID con App Roles (Lector/Editor/Aprobador/Admin) end-to-end.
  • [ ] APIM valida token y PoP/SHR → escenario HU-003 e3 (401 con token expirado/firma inválida) ejercitado por primera vez — cerrar el PENDIENTE-ENTORNO del qa-report.
  • [ ] DAST (GATE 2.5): OWASP ZAP/Burp sobre https://<swa-staging> y /api/* vía APIM → 0 críticas/altas.
  • [ ] k6 p95 < 2 s (NFR) sobre endpoints críticos; p95 < 5 s en trazabilidad/impacto.
  • [ ] Writer/reader: escrituras al primary; reportes a la réplica; lag < 30 s.
  • [ ] Alertas 5xx/latencia llegan al action group.

2.2 PRD (manual, workflow_dispatch con environment=prd)

  • GATE 3 firmado (staging validado + rollback probado, ver §4).
  • Aprobación del entorno prd en GitHub (release manager).
  • Mismo procedimiento que staging con environments/prd.tfvars.
  • Post-deploy: smoke test + revisión de alertas 24 h (ventana de observación).

3. Rollback

CapaProcedimientoTiempo estimado
Backend FunctionsRe-deploy del artefacto del commit anterior: git checkout <sha-previo> + re-run del job CD (o Azure/functions-action con el paquete anterior). Functions es stateless → rollback trivial< 10 min
Frontend SWARe-deploy del build anterior con Azure/static-web-apps-deploy desde el commit previo< 5 min
Infraestructuraterraform plan -var-file=<env>.tfvars desde el commit anterior del repo: el plan muestra el drift y apply revierte. Nunca editar recursos a mano en staging/prd10-30 min según recurso
Base de datosRestaurar a punto en el tiempo (PITR, retención 35 días): az postgres flexible-server restore. Es el último recurso — las migraciones de esquema deben ser backwards-compatible para que el rollback de código no exija rollback de datosRTO objetivo 4 h (O-1)
APIM/WAFCambios de políticas se revierten con el custodio (versionado de políticas APIM en Git corporativo)según custodio

Regla de oro: el rollback de código NUNCA debe requerir rollback de datos. Las migraciones destructivas van en dos fases (expand/contract).

4. Prueba de rollback (requisito GATE 3)

Ejecutar en staging antes del primer deploy PRD y registrar evidencia en este documento:

  • Deploy versión N en staging (CI/CD normal).
  • Deploy versión N+1 con un cambio visible (p. ej. campo nuevo en respuesta de un endpoint).
  • Ejecutar rollback a N con el procedimiento §3 (backend + front).
  • Verificar: smoke test N verde + ausencia del cambio de N+1 + cero errores 5xx en App Insights durante 15 min.
  • Evidencia: fecha, ejecutor, tiempos medidos, resultado → anexar aquí:

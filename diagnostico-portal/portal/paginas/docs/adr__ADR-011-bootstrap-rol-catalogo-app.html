Paso 1: Problem Statement

El 2026-08-20 todos los endpoints del entorno dev devolvieron error 500: la infraestructura como código había cambiado el usuario de conexión de la aplicación, pero ese usuario nunca existió en el servidor de base de datos (era un paso manual pendiente desde el Sprint 5). La recuperación exigió revertir configuración a mano, y la vía "oficial" de crear el usuario (IaC) resultó imposible: el servidor no es alcanzable desde fuera de la red privada donde corren los pipelines.

Paso 2: Last Responsible Moment

  • Fecha límite: 2026-08-20
  • Razón: incidente activo en dev; cualquier apply posterior volvería a romper el entorno mientras el rol no existiera
  • Costo de reversa: Bajo (el bootstrap es idempotente y aditivo)
  • Restricciones:
  • Presupuesto: N/A
  • Headcount: 1
  • Regulatorias: credenciales solo en el almacén de secretos (SEC-016); conexión admin sin secretos nuevos
  • Dependencias externas: N/A (precisamente la restricción de red es el motivo)

Paso 4: Opciones Consideradas

Opción A: Bootstrap por código en el arranque del backend

  • Descripción: Al crear el store, si el login como catalogo_app falla con "role does not exist", el backend abre UNA conexión como admin (secreto ya existente en Key Vault) y ejecuta de forma idempotente: CREATE ROLE, REVOKE ALL ON SCHEMA public, GRANT USAGE, CREATE ON SCHEMA public, GRANT DML en todas las tablas y ALTER DEFAULT PRIVILEGES. Corre dentro de la Function (integrada a la VNet).
  • Paved Road: Sí
  • Tecnologías: pg (node-postgres), advisory lock, Key Vault
  • Esfuerzo estimado: 1 día (con TDD: pg-mem/mock)
  • Riesgos: GRANT CREATE necesario porque las migraciones embebidas corren con el mismo usuario — deuda registrada: separar usuario de migraciones (refina SEC-013)

Opción B: Gestionar el rol con Terraform (provider postgresql)

  • Descripción: Recurso postgresql_role en IaC.
  • Paved Road: No
  • Tecnologías: Terraform provider postgresql
  • Esfuerzo estimado: 1 día
  • Riesgos: inviable verificado: el provider requiere acceso directo al puerto 5432 y el servidor tiene publicNetworkAccess=Disabled; los runners del CI están fuera de la VNet

Opción C: Mantener el paso manual por CLI/Cloud Shell

  • Descripción: Documentar y ejecutar a mano la creación del rol por entorno.
  • Paved Road: No
  • Tecnologías: psql desde Cloud Shell
  • Esfuerzo estimado: 0
  • Riesgos: la clase de error "apply cambia PG_USER sin que el rol exista" persiste; drift CLI/IaC

Detalle del Consejo

Security Engineer — 2026-08-20

Respuesta del Arquitecto: Aplicado — el diseño final usa el secreto existente, revoca primero y concede lo mínimo; la separación DDL/DML quedó como deuda registrada.

Paso 7: Decisión

Decisión Adoptada

El rol de aplicación se auto-provisiona por código en el arranque del backend (idempotente, dentro de la VNet, con el secreto admin ya existente); no por CLI ni por Terraform.

Razones Principales

  • Elimina la clase de error que causó el incidente (apply cambia PG_USER sin que el rol exista)
  • Cualquier entorno nuevo se auto-aprovisiona sin pasos manuales
  • Desaparece el drift Terraform/CLI para este recurso

Consecuencias Positivas Esperadas

  • staging/prd nacerán sin intervención manual de base de datos
  • TDD cubre: disparo solo ante "role does not exist", idempotencia, y no-disparo ante otros errores

Consecuencias Negativas Aceptadas

  • catalogo_app conserva CREATE por las migraciones embebidas — deuda: separar usuario de migraciones (refina SEC-013)

Qué NO se Decidió

  • Terraform provider postgresql: inviable por la red privada (verificado)
  • Paso manual: perpetúa el incidente

Paso 8: Re-evaluation Triggers

  • Al separar el usuario de migraciones (deuda registrada), revisar si el bootstrap sigue siendo necesario para ambos
  • Si la plataforma de Functions cambia el modelo de arranque
  • Fecha de revisión programada: al diseñar staging, o 2027-02-01

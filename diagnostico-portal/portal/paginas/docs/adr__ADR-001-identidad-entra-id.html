Paso 1: Problem Statement

Los usuarios de la organización ya tienen una identidad corporativa centralizada con políticas de acceso condicional y MFA; si la aplicación gestiona sus propias credenciales, se duplica el directorio, se incumple el lineamiento corporativo y se crea una superficie de ataque nueva (gap C-3 de la PoC: roles simulados con un selector local). Además, un token de acceso robado podría reutilizarse desde otro cliente si nada lo liga al emisor legítimo.

Paso 4: Opciones Consideradas

Opción A: Entra ID (IdP corporativo) + PoP/SHR

  • Descripción: Autenticación OIDC contra el IdP corporativo; App Roles (Lector/Editor/Aprobador/Admin) mapean el RBAC (BR-007); cada llamada valida token + prueba de posesión (BR-008) en un authorizer dedicado; MSAL en el front.
  • Paved Road: Sí (ADOPT en tech-radar)
  • Tecnologías: Microsoft Entra ID, MSAL, OAuth 2.0
  • Esfuerzo estimado: 2 semanas
  • Riesgos: dependencia del custodio para registros; tokens v1 por defecto (verificado en ADR-010 #8)

Opción B: Cognito (segundo IdP)

  • Descripción: Directorio de usuarios separado del corporativo.
  • Paved Road: No
  • Tecnologías: AWS Cognito
  • Esfuerzo estimado: 3 semanas
  • Riesgos: duplica directorio, contradice lineamiento, sin MFA corporativo

Opción C: Directorio propio en la aplicación

  • Descripción: Usuarios/claves gestionados por la propia app.
  • Paved Road: No
  • Tecnologías: tabla de usuarios + hashing propio
  • Esfuerzo estimado: 4 semanas
  • Riesgos: superficie de ataque nueva, incumplimiento regulatorio, rechazo seguro de Seguridad

Detalle del Consejo

Security Engineer — 2026-08-06

Un bearer token solo demuestra posesión de una cadena; sin PoP/SHR, un token exfiltrado es reutilizable (T-01). Los App Roles deben viajar en el access token.

Respuesta del Arquitecto: Aplicado — SEC-001/SEC-002 codifican ambas exigencias; ADR-010 #8 verificó en el despliegue real que los roles viajan en el access token.

Paso 7: Decisión

Decisión Adoptada

Entra ID como única fuente de identidad, con App Roles para el RBAC y validación de token + PoP/SHR en authorizer dedicado en cada llamada a API.

Razones Principales

  • Única opción que cumple el lineamiento corporativo sin excepción
  • MFA y Acceso Condicional heredados sin costo de desarrollo
  • Menos código de seguridad propio que mantener

Consecuencias Positivas Esperadas

  • Cero credenciales locales que proteger o rotar
  • Revocación corporativa inmediata al desvincular un usuario

Consecuencias Negativas Aceptadas

  • Dependencia del custodio del IdP para altas de app registrations
  • Ningún despliegue compartido antes de EP-02

Qué NO se Decidió

  • Cognito y directorio propio: duplican identidad y rompen el lineamiento

Paso 8: Re-evaluation Triggers

  • Que el custodio del IdP no apruebe los registros o imponga un broker intermedio
  • Que PoP/SHR no sea soportado por el gateway corporativo (verificar equivalencia con Seguridad en onboarding APIM)
